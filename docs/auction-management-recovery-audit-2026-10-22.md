# 競標管理的逾時、離線與離頁複驗

本輪延續競標與管理排查，保留先前未部署的工作；未提交、推送或部署，也未變更正式場次、付款、會員或 LINE 驗證紀錄。

## 重現及修正

新增十個瀏覽器情境，先在原實作確認失敗，再驗證修正：

| 情境             | 原行為                     | 修正                                                   |
| ---------------- | -------------------------- | ------------------------------------------------------ |
| 場次列表卡住     | 持續顯示載入中             | 整筆列表讀取最多十秒，失敗顯示重試；不回傳半份分頁結果 |
| 出價者讀取卡住   | 無法繼續查看紀錄           | 十秒退出，可重讀；保留原有完整分頁與錯誤判別           |
| 得標狀態卡住     | 持續讀取，無法管理         | 十秒退出，未確認期間不開放管理操作                     |
| 上架個體搜尋卡住 | 一直搜尋中                 | 十秒退出，可重新搜尋                                   |
| 核帳無回應       | 一直忙碌，無法確認         | 十五秒後顯示結果未確認，保存原請求供重試               |
| 上架無回應       | 一直忙碌，無法返回核對     | 十五秒後解除等待，保留原請求與參數供重試               |
| 複製成功延遲返回 | 離開場次後仍顯示舊成功提示 | 場次、會員與頁面切換使舊提示失效                       |
| 複製失敗延遲返回 | 離開場次後仍顯示舊錯誤提示 | 同上；新的複製操作也取代舊結果                         |
| 管理頁離線       | 定期重讀仍送出查詢         | 離線不自動查詢，連線恢復再同步                         |
| 離開新增場次     | 個體查詢繼續等待           | 離頁取消在途查詢與計時器                               |

共用 `createRequestDeadline` 將等待上限涵蓋 SDK 取得憑證與網路請求。取消或逾時只表示前端不再等待，不能據此推論伺服器沒有完成寫入。核帳與上架維持原本的請求編號、參數與 sessionStorage 暫存，重試沿用同一筆。

讀取在離頁、切換會員、切換場次或被新查詢取代時取消，仍保留原有代次檢查，防止晚回應覆寫新畫面。沒有改動管理操作的正式權限或既有後端交易規則。

## 唯讀資料庫核對

- 管理權限旗標目前只有一個帳號，且為使用者指定的 Google 帳號。
- `auction_admin_requests` 與 `auction_listing_requests` 均啟用 RLS，匿名不可讀、一般會員不可直接插入。
- 正式核帳及上架函式均包含管理員查核、原操作人核對與請求鎖定。這是函式定義檢查，並未實際執行正式核帳或上架。

## 驗證紀錄

- 新增的十個管理復原瀏覽器測試通過，包含逾時後恢復與重送請求完整相同。
- 共用等待上限、管理請求恢復與回執、上架欄位、登入、會員、出價契約及詳情，共五十項單元測試通過。
- 程式碼格式與差異檢查通過。

- 完整七十五項瀏覽器回歸通過，包含管理權限拒絕、超過一千筆出價分頁、上架與核帳回執遺失、同筆請求恢復、不同場次限制、預約開標、LINE 登入、官方驗證及領標流程。
- 隔離正式建置成功，程序結束碼為零；最新產物的六項 SSR 檢查通過：最高價、無出價、資料故障不捏造價格、結標禁止索引、詳情及列表資料不可注入腳本。

## 驗證界線

瀏覽器操作採本機實際頁面及 SDK，資料與寫入回應均為隔離測試。正式 Supabase 只做權限、函式及表設定的唯讀檢查，未向客戶發送訊息、未執行真實核帳或新增正式場次。
