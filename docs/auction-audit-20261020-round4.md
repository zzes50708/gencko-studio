# 競標與管理持續複驗第四輪（2026-10-20）

本輪依要求持續排查與修正至額度接近不足。測試通過不代表正式環境已部署，也不代表已排除所有風險。

## 已修正的問題

1. 管理出價者 RPC 受單次 API 上限影響，超過一千筆可能漏掉會員與出價次數。改為每頁 500 筆、固定排序、去重與完整讀取；中途失敗不回傳部分結果。切換場次、帳號及離頁取消舊查詢。
2. 會員得標列表未包含 `claimed_at`，與詳情的 LINE 領標狀態不一致。資料庫列表補上欄位並驗證只可讀自己的資料。
3. 會員重讀得標紀錄時仍能發起付款／棄標／複製操作。讀取期間停用相關操作。
4. 出價結果待確認時換帳號，舊請求可能殘留在畫面。帳號切換清除顯示，保留原帳號暫存供恢復。
5. 原帳號延遲回執可能影響新帳號。現在只清理原請求與其原帳號暫存，不彈出另一帳號的成功通知。
6. 重試遇到登入過期，不能代表原出價未成立。401 保留原請求，同帳號重新登入可繼續確認。
7. 恢復待確認請求時顯示原金額與暱稱，不顯示另一個新最低價來誤導重試內容；成功後清除 ID／email 兩份舊暫存。
8. 嚴格驗證待確認請求，移除額外欄位；先檢查每份暫存再選取，避免毀損的 ID 暫存遮蔽有效的 email 暫存。
9. 舊 `end-auction` 原始碼會跳過現行得標流程、將競標個體改回待售。確認正式環境沒有此函式或排程後，將原始碼改為 410 停用回應，且本機設定要求 JWT，避免日後誤部署。未部署這個舊入口。
10. 公開場次列表與 SSR 清單改為完整分頁讀取，並共用 48 小時保留範圍；SSR 不再讓歷史場次擠掉有效資料。
11. 大量場次查價分成每批 100 個 ID，避免查詢網址過長；空回執不再誤認為無人出價。
12. 已付款／已取消不再顯示催付款指引或付款期限；棄標也有對應說明。
13. 上架暫存逐欄驗證、只恢復允許參數並標準化 UUID。已過期的原請求仍可重試取回既有回執。
14. 「直購」原先僅開啟 LINE，文案卻像已能直接成交。改為「詢問直購」，明確說明不保留、不結標，最高出價已達直購價時停用詢問。
15. 管理頁補上即時事件、重新連線、恢復上網與可見頁面定時補查，更新場次、出價者與得標狀態；保留管理理由，避開待確認操作與棄標確認。離頁／換帳號讓舊背景工作失效。
16. 會員頁恢復上網及可見時補查核帳結果；內容未變沿用原資料物件，不清除客人剛產生的領標訊息。
17. LINE 暱稱服務失敗原先會阻擋已驗證的領標事件。函式改為輔助查詢失敗仍保存事件，身分仍需簽章、來源及資料庫驗證碼核對；無效事件先排除，避免無謂查詢。
18. LINE 暱稱為空會抹去既有名稱。資料庫改為同一 LINE 身分保留既有名稱，有新名稱才更新；換身分不沿用舊名稱。
19. 舊 email 帳號後來綁定 Google／LINE 時，前端可能判定為其他登入方式。改採與伺服器一致的受信任供應商清單，不讀使用者可修改的 metadata 作授權。
20. 為列表與詳情 JSON-LD 增加明確轉義，保留原始文字。最初以 HTML 原始字串檢查誤判為腳本注入；後改用真實瀏覽器，且重跑第三輪舊正式建置，兩者都沒有執行腳本。這是額外防護，**不是已證實漏洞或已修復漏洞的證據**。未轉義的獨立對照 HTML 確實會執行，證明測試能偵測此類情況。
21. 舊 SSR 測試寫死真實場次最高 400 元，該場早已結標。改為獨立假 API 加正式 SSR 建置驗證，不修改既有場次來配合測試。
22. 同一管理員憑證更新產生新使用者物件時，不再誤判成換帳號而關閉場次、清掉尚未送出的管理理由；已用瀏覽器複驗。

- 14 個指定單元／API 測試檔，52 項通過；其中 H3 API 子程序另涵蓋 16 種回應情境。
- 主競標瀏覽器組 25 項通過；其中出價安全組含 19 個故障／競爭情境。最新暫存修正後另重跑該組通過。
- 照片、鍵盤、觸控及版面 10 項通過。
- 正式 PWA 離線競價快取與時間 API 2 項通過。
- 10 組資料庫腳本合計 110 個斷言通過；LINE 函式修改後重跑相關結算／領標／期限／名稱組。101 場跨批次結算、未開標保留、無人出價不產生假得標者亦通過。各組無殘留測試場次。
- 瀏覽器主要使用模擬 API／WebSocket；資料庫測試是真的執行資料庫交易，但不是正式客戶高流量壓力測試。
- 本輪不發送 LINE 訊息、不新增付款義務。
- 最新隔離正式建置通過，程序結束碼 0，輸出 `output/auction-round4-build.log`。最後的管理員同帳號更新修正已納入；管理組 10 項另重跑通過。
- SSR 六項隔離檢查通過，使用假 API 加正式建置，並以真實瀏覽器檢查指定腳本字串沒有執行、JSON-LD 仍可解析；另確認舊第三輪建置也通過這個腳本檢查，不把最初字串比對誤判算成漏洞。
- 最後確認測試場次無殘留，正式設定仍為 processing／auto-enroll 開啟、manual_claim、notifications 關閉。

## 尚未解決的高優先風險

共用 `public.animals` 的 RLS 關閉，訪客與一般會員有直接改寫權限；已確認訪客 INSERT／UPDATE／DELETE 皆為 true。另一個 `gencko-admin` 後台目前沒有登入流程，直接以訪客權限維護個體資料。因此不能只在此專案撤權，否則另一後台會立即無法維護個體。這不是抽象警示，應在正式販售前協調修正。具體後續見 [共用資料權限修正計畫](auction-shared-data-access-followup.md)。本輪未改寫另一專案或直接切斷其權限。

競標場次與出價表的訪客／一般會員直接寫入權限皆關閉。管理 RPC 雖允許會員呼叫，仍由資料庫檢查真正的管理員設定；LINE 事件、結算及通知 RPC 僅伺服器角色可執行。公開出價資料只授予 ID、場次、顯示暱稱、金額及時間欄位；已查核 Realtime 實作會依欄位可讀權限過濾，未開放 email／會員 ID 欄位。

效能顧問有競標外鍵缺索引 INFO，但目前只有 2 場、3 筆請求，且實際出價最高價查詢已有複合索引。本輪未僅為消除提示而盲目新增所有索引。其他全站 RLS、檢視及重複索引提示不屬本輪修正範圍。

## 部署狀態與實際邊界

- 資料庫兩項修正已生效。
- 網站前端／API 與 `auction-workflow` 的本輪修改尚未部署；不能把本機驗證當成正式站已修好。
- 目前流程仍為得標者自行 LINE 領標、工作室人工核帳、結標後 24 小時付款及結標頁保留 48 小時。
- 限制可涵蓋帳號與已驗證 LINE 身分，不能保證辨認完全不同且未綁定的新帳號是同一個人。
